# Neocortex v2 — архитектура мультиагентной системы

Продолжение анализа прототипа (`docs/prototype-analysis.md`). Здесь — целевая схема с учётом ограничений: единственный исполнитель — Orange Pi Zero 2W (4 ядра, 969 МБ RAM, своп 484 МБ), реальный параллелизм = 1, лимиты подписок Codex/Claude не жёсткие.

---

## 1. Что говорит текущая практика

Три вывода, на которых стоит вся схема ниже.

1. **Мультиагентность оправдана ровно тремя вещами:** параллельная широта, изоляция контекста и независимая верификация ([Anthropic, multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system); обзор паттернов и отказов — [cazyweb, 2026](https://cazyweb.com/research/multi-agent-llm-systems-orchestration-patterns/)). Параллельная широта нам недоступна физически. Значит, наши агенты существуют ради **изоляции контекста и независимой проверки** — и число ролей должно быть маленьким, иначе мы платим токенами за театр.
2. **Большинство отказов мультиагентных систем — координационные, а не модельные** (Cemri et al.): неоднозначные роли, недоспецифицированные передачи, отсутствие стадии, которая имеет право отклонить работу. Наш прототип попал ровно в этот класс.
3. **Оркестрация должна быть обычным кодом, а не переговорами агентов.** Свободный чат агент-агенту — это канал, по которому теряются и выдумываются ограничения. Передача — типизированный артефакт, который может прочитать валидатор или человек. Anthropic отдельно отмечает: агенты сегодня плохо координируют друг друга в реальном времени, и координацию лучше держать в коде.

Отдельно: Anthropic измерили, что мультиагентная схема жжёт ~15× токенов относительно чата. При наших лимитах это терпимо, но это аргумент за то, чтобы критик и планировщик были дешёвыми ролями с узким контекстом.

---

## 2. Ключевая идея: агенты — это корутины, а не процессы

Твоё требование — краб поднимает агентов с параллелизмом 1, но «они не должны об этом знать», и исполнение должно переходить между ними, когда один ждёт ответа другого.

Это в точности кооперативная многозадачность. Реализуется так:

- **Единица исполнения — turn** (один запуск CLI-сессии, ограниченный по времени и контексту).
- **Агент — не процесс, а запись в БД:** цель, критерии приёмки, входящий ящик, журнал решений, ссылка на рабочую ветку. Живёт между турнами.
- **Турн всегда заканчивается одним из четырёх исходов** (агент обязан вернуть машинно-читаемый результат):
  - `DONE {artifact}` — работа завершена, артефакт приложен;
  - `ASK {to, question}` — нужен ответ другого агента или владельца → агент переходит в `BLOCKED`, **процесс завершается**;
  - `YIELD {note}` — работа продолжается, но турн исчерпан → `RUNNABLE`;
  - `FAIL {reason}` — не смог.
- **Ожидание не занимает ресурсов.** Агент не «висит», он не существует, пока ему нечего делать. Планировщик будит его, когда в ящик приходит ответ. На 1 ГБ RAM это единственный работающий вариант, и он же даёт неограниченное логическое число агентов.
- **Контекст турна собирается кодом**, а не «прочитай все наши файлы»: brief = цель + критерии + новые сообщения из ящика + сжатый журнал решений + diff рабочей ветки. Размер brief ограничен и измеряется. Никаких 75 КБ Markdown на старте.

Это же снимает проблему «сессия прервалась по таймауту и всё потеряно»: состояние живёт в БД, а не в контексте модели.

## 3. Роли

Минимальный набор. Роль добавляется только тогда, когда без неё ломается конкретный сценарий.

| Роль | Исполнитель | Вход | Выход | Право отклонить |
|---|---|---|---|---|
| **Planner** | LLM (дешёвая модель) | цель проекта, фидбек владельца, инциденты | задачи с машинно-проверяемыми критериями приёмки | — |
| **Worker** | LLM (сильная модель) | одна задача + её критерии + рабочая ветка | коммиты в своей ветке + отчёт | — |
| **Critic** | LLM, отдельная сессия | **только** diff + критерии приёмки | `pass` / `rework(причины)` / `reject` | да |
| **Arbiter** | детерминированный код | вердикты, результаты тестов, счётчик попыток | merge / rollback / эскалация владельцу | да |
| **Scheduler** | детерминированный код | очередь агентов | запуск одного турна | — |
| **Owner proxy** | код + уведомления | вопросы к владельцу | ответы в ящики агентов | да |

Критик **не видит отчёт worker'а** — иначе он рецензирует нарратив, а не изменение. Это прямое лекарство от «исполнитель сам себе приёмщик».

Arbiter намеренно не LLM: подсчёт вердиктов, прогон тестов, лимит попыток и решение о merge — детерминированные операции, суждение там не нужно.

## 4. Протокол обмена

Свободного текста между агентами нет. Есть шесть типов сообщений, все — JSON с валидируемой схемой:

```
task_assignment  { task_id, objective, acceptance[], boundaries[], budget }
question         { from, to, task_id, question, blocking: true }
answer           { to, question_id, answer }
review_request   { task_id, branch, diff_ref, acceptance[] }
review_verdict   { task_id, verdict: pass|rework|reject, findings[] }
incident         { kind, evidence_ref, severity }
```

`task_assignment` намеренно повторяет вывод Anthropic про делегирование: у подзадачи должны быть цель, формат вывода, границы и бюджет — иначе исполнители дублируют работу или расходятся в трактовке.

## 5. Планировщик

```
while budget_remains and not stop_requested:
    preflight()                      # модель отвечает, память есть, тесты на HEAD зелёные
    agent = pick_runnable()          # приоритет: инциденты > фидбек > активные задачи > груминг
    outcome = run_turn(agent)        # один процесс CLI, жёсткий таймаут, лог трассы
    apply(outcome)                   # доставка сообщений, смена состояний, запись стоимости
    detect_deadlocks_and_starvation()
```

Свойства, каждое из которых закрывает конкретный сбой прототипа:

- **Preflight-гейт.** Один дешёвый вызов модели перед циклом. Сегодняшний crash-loop (`gpt-6-astra` не поддерживается CLI 0.150.1, 130 пустых сессий подряд) отсекается на первой попытке и поднимает инцидент вместо перезапуска.
- **Circuit breaker.** N однотипных провалов подряд → ветка работы останавливается, инцидент, уведомление наружу. Не бесконечный retry.
- **Граф ожиданий.** `ASK` строит ребро; цикл в графе = взаимоблокировка → эскалация владельцу, а не тихий висяк. У каждого `ASK` есть таймаут.
- **Лимиты на размножение.** Максимум живых агентов, максимум глубины делегирования, максимум турнов на задачу. У Anthropic ранние версии спавнили 50 подагентов на простой запрос; при параллелизме 1 такая ошибка означает вечную очередь.
- **Прогресс, а не живость.** Health-check спрашивает «сколько задач принято арбитром за последние N часов», а не «жив ли процесс». Прототип показывал «работает» во время 130 подряд падений.
- **Учёт стоимости** на турн: модель, время, токены (если CLI отдаёт), исход. Это единственный способ понять, окупается ли критик.

## 6. Состояние и изоляция

- **SQLite** — единственный источник истины: `agent`, `task`, `message`, `run`, `feedback`, `decision`, `incident`, `artifact`. Транзакции решают гонки, из-за которых в прототипе появились «атомарные публикации», «crash-safe компакция» и «предотвращение гонок компакции» — три класса задач, которых в новой схеме не существует.
- Markdown — **генерируемое** представление для чтения и для git-истории, не хранилище.
- **Каждая задача = git worktree + ветка.** Откат = удалить ветку. Worker физически не может сломать чужую работу.
- **Агент не правит рантайм, в котором исполняется.** Планировщик запускает released-версию (`/opt/neocortex/current`, симлинк на тег), рабочая копия отдельно; применение = отдельный шаг с тестами, health-check и автооткатом. Это лечит T062/T065, где правка `orchestrator.sh` не доезжала до живого процесса 12+ часов.

## 7. Откуда берутся задачи

Порядок при простое:

1. Необработанный фидбек владельца.
2. Инциденты.
3. Явный бэклог реальных проектов (issues / TODO в репозиториях).
4. Найденные дефекты реальных проектов.
5. Платформа — квота не более ~20% турнов и только с явным критерием приёмки.

Без наполненных пунктов 3–4 система снова выродится в самообслуживание: 55 из 55 закрытых задач прототипа были про его собственную обвязку.

**Idle — валидный успешный исход.** «Проверяемой работы нет, вот три предложения» лучше, чем изобретённая задача про ротацию логов.

## 8. Оценка качества

Без этого нельзя понять, помогает ли критик или просто жжёт токены.

- Набор из 10–20 записанных задач-кейсов; прогон схемы на них после изменений в промптах/ролях.
- LLM-судья по фиксированному чеклисту для субъективных исходов + детерминированные проверки там, где возможно.
- Метрики: доля турнов, закончившихся принятым арбитром результатом; доля отклонённых критиком изменений, которые действительно были плохими (точность критика); время ответа на фидбек; доля турнов на платформу vs на проекты; инциденты и MTTR; стоимость задачи.

## 9. Реализация

```
neocortex/
  nc/
    scheduler.py      # цикл, preflight, circuit breaker, граф ожиданий
    state.py          # SQLite, схема, миграции
    turn.py           # сборка brief, запуск CLI, парсинг исхода
    protocol.py       # схемы сообщений и валидация
    roles/            # промпты Planner / Worker / Critic
    adapters/         # codex_cli.py, claude_cli.py
    arbiter.py        # тесты, вердикты, merge/rollback
    notify.py         # telegram/matrix
    views.py          # генерация Markdown и данных для дашборда
  dashboard/          # read-only, читает БД
  tests/
  docs/
```

Порядок работ (в сессиях):

- **S0.** Каркас: SQLite-состояние, планировщик с одним турном, адаптер Codex CLI, preflight, circuit breaker. Прогон на одной настоящей задаче.
- **S1.** Протокол сообщений, `ASK/ANSWER`, ящики, граф ожиданий. Здесь появляется настоящая многоагентность.
- **S2.** Worker в worktree + Critic + Arbiter. `DONE` только через арбитра.
- **S3.** Фидбек-цикл с состояниями и уведомлениями наружу; дашборд поверх БД.
- **S4.** Источник задач из реальных проектов, квота на платформу, метрики и набор кейсов для оценки.
- **S5 (по желанию).** Раннер-протокол: краб остаётся контроллером, тяжёлые турны уходят на ПК/VPS. Схема к этому готова — параллелизм становится параметром планировщика.

## 10. Что осознанно не делаем

- Свободные дискуссии агентов и «совещания» — главный источник координационных отказов.
- Роль на каждую функцию. Больше ролей ≠ надёжнее; голосование трёх одинаково ошибающихся моделей — дорогая иллюзия.
- LLM там, где хватает кода: тесты, линтеры, парсинг, приоритеты, merge.
- Тяжёлые фреймворки (AutoGen/LangGraph-графы). Их гибкость — это ровно та поверхность отказов, от которой мы уходим; наш цикл — 200 строк питона.
