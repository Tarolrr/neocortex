## 1. Состояние прямо сейчас (факты, не оценки)

- **Система в crash-loop.** `codex-cli 0.150.1` не умеет `gpt-6-astra`: каждый ран падает за ~4 секунды с HTTP 400 `The 'gpt-6-astra' model requires a newer version of Codex`. Оркестратор перезапускает агента каждые ~14–25 секунд.
- **130 сессий за сегодня — все пустые.** Ни одна задача не сдвинулась. `T066` и `T067` (твои wake-up) висят в `[TODO]`.
- **Через несколько минут всё умрёт молча.** Цикл 490 из `MAX_CYCLES=500`; на лимите оркестратор просто выходит с записью в лог. Никто не узнает до следующей пятницы.
- **Дашборд при этом показывает «работает».** Watchdog следит только за живостью `ai-dashboard`, а не за тем, что агент что-то сделал. Успех и 130 подряд падений выглядят одинаково.
- Память: 578 МБ свободно, своп 304/484 МБ занят. Это потолок; параллельные сессии на этом железе невозможны в принципе.

Немедленный фикс — обновить Codex CLI или временно вернуть валидную модель. Но это симптом, а не причина.

## 2. Почему прототип «не очень заработал»

### 2.1. Уроборос: система работает только над собой

55 из 55 завершённых задач — обслуживание собственной обвязки: бэкапы `dashboard.py`, ротация логов, компакция координационных файлов, гонки watchdog, «recompact coordination files after the keep window regrew **again**» (это заголовок трёх разных задач). Ценности вне системы не создано ни на одну задачу.

Это не лень агентов, это следствие правила «нет активной задачи — найди себе работу». Единственный код, который агент видит, — он сам. Автопоиск задач без внешнего источника ценности **всегда** сходится к самообслуживанию: у платформы бесконечно много мелких дефектов, и каждый из них — валидная, тестируемая, приятно закрываемая задача.

### 2.2. Markdown одновременно БД, очередь, промпт и UI

Это агенты диагностировали сами и верно. Следствия: позиция в файле = семантика (T049: новая задача архивировалась компактором в том же цикле, в котором создавалась), парсер хрупкий, компакция теряет контекст, дашборд рендерит внутреннюю кухню как информационную архитектуру.

### 2.3. Агент правит процесс, внутри которого сам исполняется

T062 переключил цикл на Codex-only правкой `orchestrator.sh`, но живой процесс держит тело цикла в памяти. Изменение не применялось 12+ часов, Claude продолжал брать задачи, отложенный «guarded restart» отвалился по одноразовой предусловной проверке и не был повторён. Обнаружил это **ты**, а не система. Нет инварианта «изменение доехало до рантайма» — только «файл отредактирован».

### 2.4. Исполнитель сам себе приёмщик

`[DONE]` ставит тот же агент, который делал работу, а `RESULTS.md` — его же самоотчёт. Независимой проверки нет, поэтому единственная наблюдаемая метрика прогресса — объём убедительного текста в отчёте. Отсюда абзацы на 15 строк про то, как аккуратно всё сделано, при нулевом внешнем эффекте.

### 2.5. Реакция на фидбек не была частью протокола

Твоя претензия «два фидбека висят неотвеченными» — прямое следствие: `Addressed by` — ручная строка, означающая одновременно «увидел», «ответил», «запланировал» и «проверил». Нет инварианта «ни один фидбек не остаётся без диспозиции к концу сессии», нет состояний, нет отдельного «жду твоего ответа».

### 2.6. Контекст съедает сессию

Старт сессии: `SHARED_MEMORY.md` 28 КБ + `RESULTS.md` 20 КБ + `TASKS.md` 16 КБ + `DISCOVERIES.md` 11 КБ + `AGENT.md`. При лимите 15 минут заметная часть бюджета уходит на чтение собственной истории. Компакция это лечит симптоматически — и порождает ещё один класс задач про компакцию.

### 2.7. Мультиагентности фактически нет

«Codex → Claude → Codex» по одной общей очереди — это не взаимодействие, это один и тот же процесс с разными весами модели. Нет разделения ролей, нет независимой критики, нет арбитра, нет разных точек зрения на один артефакт.

## 3. Предлагаемая архитектура

### 3.1. Три принципа

1. **Разделить плоскости.** Control plane (состояние, очередь, политика, бюджеты) — Execution plane (эфемерные сессии агентов) — Presentation (дашборд). Агент не пишет в состояние напрямую: только через CLI/API с валидацией.
2. **Агент никогда не правит процесс, в котором исполняется.** Harness живёт в git (`neocortex`), рантайм запускает *released*-версию, агент правит рабочую копию → тесты → отдельный шаг apply с рестартом, health-check и автооткатом.
3. **Что можно проверить кодом — не отдавать LLM.** Тесты, линтеры, парсеры, валидаторы, вычисление приоритета — детерминированный код. LLM — только там, где нужно суждение.

### 3.2. Состояние

Вместо Markdown и вместо JSON-per-file (их текущее предложение) — **SQLite**: одна файловая БД, транзакции и уникальность бесплатно, никаких гонок и «атомарных публикаций», запросы вместо парсинга. Markdown остаётся *генерируемым* представлением для чтения и для git-истории.

Сущности: `project`, `task` (с machine-checkable `acceptance`), `feedback` (со state machine), `run` (агент, модель, стоимость, исход), `decision` (что ждёт владельца), `incident`.

### 3.3. Роли

| Роль | Кто | Что делает | Что НЕ видит |
|---|---|---|---|
| **Groomer** | LLM | Превращает фидбек/цели в задачи с проверяемыми критериями приёмки | Код не пишет |
| **Worker** | LLM | Делает одну задачу в изолированном git worktree/ветке | Не закрывает задачу сам |
| **Critic** | LLM, отдельная сессия | Видит только diff + критерии приёмки, выносит pass/fail/rework | Самоотчёт worker'а |
| **Arbiter** | Детерминированный код | Гоняет тесты, применяет политику (лимит попыток, вето критика), мержит или откатывает | — |
| **Health** | Скрипт | Следит за *прогрессом*, а не за живостью процесса | — |

Критик без самоотчёта автора — ключевая деталь: иначе он ревьюит нарратив, а не изменение.

### 3.4. Правила робастности (прямо против того, что сломалось)

- **Definition of Done формулируется до начала работы и машинно проверяема** (тест, HTTP-код, инвариант на diff). Нет проверяемого критерия → задача не идёт в работу, а идёт к владельцу как вопрос.
- **Закрывает задачу арбитр, не исполнитель.**
- **Preflight-гейт перед каждым раном:** модель отвечает (один дешёвый вызов), квота есть, память есть, тесты на HEAD зелёные. Не прошло — инцидент, а не запуск. Это ловит сегодняшний сбой на первой же попытке.
- **Circuit breaker:** N подряд однотипных провалов → остановка ветки работы, инцидент, уведомление. Сегодня было 130 попыток без единого сигнала.
- **Изоляция:** сессия = ветка/worktree, откат = удалить ветку.
- **Бюджеты:** время, токены, сессии/сутки — учитываются по задачам и видны в дашборде.
- **Уведомления наружу** (Telegram/Matrix/почта). Ты не сидишь в дашборде. Событий ровно три: *нужен твой ответ*, *инцидент*, *готово к ревью*.
- **Idle — валидный успешный исход.** «Проверяемой работы нет, вот три предложения» лучше, чем самозаверчивание.

### 3.5. Откуда берутся задачи (лекарство от уробороса)

Приоритет при простое, сверху вниз:

1. Необработанный фидбек владельца.
2. Инциденты и блокеры.
3. Явный бэклог проектов (issues, TODO в реальных репозиториях).
4. Улучшение реальных проектов: найденные баги, непокрытые тесты, регрессии.
5. Улучшение платформы — **с жёсткой квотой** (например, не более 20% циклов) и только с явным критерием приёмки.

Без пункта 3–4, заполненного настоящими проектами, любая такая система выродится в то, что ты видел.

### 3.6. Топология: где реально запускать параллельные сессии

Orange Pi (1 ГБ RAM) не исполнитель. Он — **контроллер**: состояние, дашборд, планировщик, уведомления. Исполнение выносим на ноды с ресурсами — рабочий ПК (`tarolrr-pc` / `tarolrr-hp`), VPS или Devin-сессии. Tailscale уже даёт сеть; нужен простой раннер, который забирает задачу из очереди контроллера, выполняет её в своём worktree и отдаёт результат.

Так «много независимых сессий с арбитром» становится реализуемым: 1 контроллер + N раннеров, N ограничено железом и подпиской, а не архитектурой.

### 3.7. Где мультиагентность даёт выигрыш, а где вредит

**Даёт:** независимая критика диффа; генерация 2–3 вариантов плана с выбором по критериям; отдельная red-team сессия «чем это сломать»; разделение «планирует один, делает другой» (планировщик не влюблён в свою реализацию).

**Вредит:** роль-на-каждый-чих; текстовые «дискуссии» агентов (латентность, цена, дрейф темы); LLM там, где хватает `pytest`. Консенсус трёх агентов, каждый из которых ошибается одинаково, — это не надёжность, а дорогая иллюзия.

## 4. Дорожная карта (в сессиях, не в неделях)

- **Сессия 0 (сейчас):** починить crash-loop; preflight-проверка модели; circuit breaker; вынести код в `neocortex` под git; запретить самомодификацию рантайма.
- **Сессия 1:** SQLite-состояние + CLI (claim/close задачи, диспозиция фидбека); генерируемые Markdown-представления; дашборд читает БД.
- **Сессия 2:** worker в worktree + арбитр (тесты + критик); `DONE` только через арбитра.
- **Сессия 3:** протокол раннера (контроллер на crab, исполнение на мощной ноде); параллельные сессии; бюджеты; уведомления наружу.
- **Сессия 4:** источник задач из реальных проектов; квота на платформенные задачи; метрики.

## 5. Метрики вместо счётчика задач

- Доля сессий, закончившихся результатом, принятым арбитром.
- Время ответа на фидбек; количество фидбеков без диспозиции (целевое — 0).
- Доля циклов на платформу vs на реальные проекты.
- Инциденты: количество, MTTR, доля восстановленных автоматически.
- Стоимость задачи: время, токены, деньги.
